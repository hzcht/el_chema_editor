# ALGORITHMS.md — как устроены алгоритмы редактора

Документ отвечает на вопрос «**как и почему** работает код», а не «что требуется».

| Документ | Роль |
|---|---|
| `ideas.md` | Требования и правила продукта (§4.6 — трассировка, §13.3 — roadmap) |
| `DECISIONS.md` | Принятые решения и отвергнутые альтернативы (ADR-0004…0007) |
| `problems.md` | Журнал ошибок: Problem → Fixed → Closed |
| `AGENTS.md` | Сжатые правила для агентов и gotcha |

**Разграничение «комментарий в коде ↔ документ».**
В коде остаётся контракт: одна строка «что делает», pre/post, какое правило
нельзя нарушить, и ссылка вида «см. `docs/ALGORITHMS.md` §1.5». Всё остальное —
пошаговые разборы, мотивация, отвергнутые варианты, история отладки — здесь.
Номера § ниже стабильны: на них ссылаются комментарии и тесты.

## 1. Маршрутизация проводников (`internal/geom/geom.go`)

Константы приложения (мм): `outset` = 5 — отступ выхода от пина, `pinGap` = 2 —
зазор до чужого пина, `laneGap` = 2 — разводка наложений, `stickyMM` = 3 —
гистерезис стороны обхода, `arcR` = 1.6 — радиус мостика (см. `cmd/shbuilder/main.go`).

### 1.1 `Route` — базовый маршрут пин → пин

Вход: точки пинов `p1`, `p2`, их стороны `s1`, `s2`, отступ `out`. Каждая сторона
даёт точку выхода за габарит: `e = p + normal(side) * out`; нормаль — **наружу**
(Y растёт вниз, `Side.Normal`).

`pathFor` выбирает форму по ориентации сторон и их взаимному положению:

- **обе горизонтальные (L/R)**
  - стороны противоположны и «вперёд» (`Right` при `e1.X ≤ e2.X`, `Left` при
    `e1.X ≥ e2.X`): при `e1.Y ≈ e2.Y` — одна прямая `p1→p2` (минимум колен),
    иначе зигзаг через средний `x = (e1.X+e2.X)/2`;
  - стороны противоположны, но «назад» — обход по среднему
    `y = (e1.Y+e2.Y)/2` (иначе маршрут шёл бы против нормали выхода);
  - одна и та же сторона — обход по среднему `x`.
- **обе вертикальные (T/B)** — зеркально: средний `y` для «вперёд», средний `x`
  для «назад» и для одной стороны.
- **горизонталь → вертикаль**: единственное колено `K = (e1.X, e2.Y)`.
- **вертикаль → горизонталь**: `K = (e2.X, e1.Y)`.

`SideNone` (резиновая скрутка, пин без стороны) — L-колено по `x`:
`p1 → (p2.X, p1.Y) → p2`.

После `Clean` остаётся не более двух изломов и ни одного наклонного сегмента.

### 1.2 `Clean` — нормализация ломаной

1. Убирает подряд идущие дубли (сравнение `near`, `eps = 1e-4`).
2. Схлопывает коллинеарные промежуточные точки **только при монотонном
   продолжении** (`(c-b)*(b-a) > 0`). Точка разворота (hairpin) сохраняется:
   удалив её, мы стёрли бы разворот из геометрии, и детектор `Hairpins` перестал
   бы видеть «крюк».

### 1.3 Препятствия: `Obstacle`

```go
type Obstacle struct { Rect Rect; Gap float32 }
```

- `Gap > 0` — зона запрета «прямоугольник + зазор»: маршрут не заходит даже в
  зазор, провод идёт с отступом от кромки обтекаемого блока.
- `Gap == 0` — только «не резать внутренность». Так задаются **собственные блоки
  линка**: пин лежит на кромке, и зона вокруг него сделала бы любой подход к пину
  нарушением (обход зацикливался бы петлёй вокруг пина — «флажок»). Штырь-заглушка
  у пина лежит на кромке и не детектируется.
- Прямоугольник **нулевого размера** — это точка (чужой пин): маршрут обязан
  пройти не ближе `Gap`, иначе провод визуально «втыкается» в точку подключения.

### 1.4 `RouteAvoid` — обёртка для простого случая

Строит `RouteOpts` из двух наборов прямоугольников: чужие блоки получают
`Gap = out`, собственные (`self`) — `Gap = 0`, и вызывает `RouteEx`.
Отдельный список `self` появился потому, что раньше собственные блоки
исключались вовсе, и линк `A.0→B.0` резал собственный блок `A`.

### 1.5 `RouteEx` — итеративный обход препятствий

1. Стартует с `Route` (базовая форма).
2. Цикл: `iter < 10 && detours < 64`. Для каждого сегмента `route[i-1]→route[i]`
   и каждого препятствия проверяется пересечение — **сначала зона запрета**
   `expandRect(rect, Gap)`, затем сам прямоугольник. Для `Gap == 0` проверка одна.
   Порядок важен: сегмент, начавшийся внутри зоны, зона не видит
   (eps-семантика `SegCrossRect`), а сквозь блок нельзя в любом случае.
3. `SegCrossRect` возвращает только вход **снаружи внутрь**. Если точка входа
   совпала с концом сегмента (`near(pt, b)`) — сегмент лишь касается границы,
   это не «сквозь», обход не нужен.
4. Найденное место обхода запоминается в `seen` как `(номер препятствия, точка
   входа)`. Повторный обход там же запрещён: он дал бы петлю («лепесток»),
   растущую до лимита итераций.
5. `detourAround` перестраивает маршрут; если результат совпал с текущим
   (`samePath`) — шаг не засчитывается, иначе счётчик крутился бы вхолостую.
6. После любого успешного обхода скан начинается заново (`fixed`): геометрия
   изменилась, прежние проверки устарели. Нет изменений — выход.
7. На выходе — `Clean`.

Лимиты (`10` итераций, `64` детура) — предохранитель от патологических сцен,
а не часть эвристики.

### 1.6 `detourCandidates` — набор вариантов обхода

Для сегмента `a→b` вокруг препятствия `obs`:

- Границы зоны запрета: `obs ± out` по каждой оси.
- Точка входа — ближняя к `a` граница зоны (`zMinX`, если `a` левее блока,
  иначе `zMaxX`). Если эта граница **позади направления движения**
  (`(b.X-a.X)*(enterX-a.X) < 0`), вход прижимается к `a`: назад не откатываемся.
- Перебираются две стороны обхода (выше/ниже для горизонтального сегмента,
  слева/справа для вертикального). Сторона, совпавшая с текущей линией,
  пропускается — обход выродился бы в ноль.
- Для каждой стороны два варианта:
  - **с возвратом** на исходную линию у `b` — классический обход;
  - **без возврата** — только если следующий сегмент коллинеарен движению
    (`route[segIdx+2].X ≈ b.X` для горизонтали): продолжение идёт вдоль `b.X`,
    и возврат создавал бы «крюк».
- Каждый кандидат нормализуется `Clean` и сравнивается с исходным маршрутом;
  кандидаты оцениваются **по всему маршруту**, поэтому сторона обхода
  выбирается с учётом того, куда маршрут идёт дальше.

Одно фиксированное правило обхода не годится: возврат на исходную линию у точки
`b` в части случаев продолжения маршрута давал крюк (ПР-1).

### 1.7 Выбор варианта: крюки → длина → гистерезис

`detourAround`:

1. Основной критерий — `Hairpins(cand)`: меньше крюков лучше; при равенстве —
   короче (`pathLen`).
2. Гистерезис (`sticky > 0` и есть `prev`): среди кандидатов с тем же числом
   крюков и длиной не больше `bestL + sticky` выбирается тот, что ближе к
   прошлому маршруту (`routeDist`). Так сторона обхода не перескакивает от
   микросдвига блока (ADR-0007).
3. `routeDist(a, b)` — сумма манхэттенских расстояний от каждой вершины `a` до
   ближайшей вершины `b`. Вершины обхода по разные стороны блока разнесены на его
   высоту/ширину, поэтому «своя» сторона даёт заметно меньшее значение, а общие
   участки — нулевой вклад.

`RouteOpts.Prev` используется **только для выбора стороны**: геометрия прошлого
маршрута не переиспользуется. Память лежит в `editor.lastRoutes` по ключу линка
`from->to`.

### 1.8 `Hairpins` — детектор крюков

Крюк — три подряд точки с одной координатой, между которыми направление меняется
на противоположное: вертикаль вниз и сразу вверх тем же `x` (или горизонталь
вправо-влево). Именно это заметил пользователь: «идёт горизонтальная линия…
уходит вниз… меняет направление вверх с сохранением `x`».

**Правило трассировки (§4.6):** маршрут не должен содержать ни одного крюка.
`Hairpins(route) == 0` — контракт, на который опираются тесты
(`TestRouteAvoidNoHooks`, `TestDemoLinksNoHooks`, `TestManyLinksNoHooks`).

### 1.9 Пересечения: `SegCross`, `SegCrossRect`

- `SegCross` — точка пересечения двух **осевых** отрезков (H×V). `false` для
  параллельных, вырожденных и касающихся только на концах: касание на конце —
  это узел (общий пин), а не пересечение проводников, мостик там не рисуется.
- `SegCrossRect` — точка входа осевого отрезка в прямоугольник. Возвращает
  `true` только при движении **извне внутрь**. Выход изнутри наружу игнорируется:
  уже декорированный сегмент иначе зацикливал бы обход. Кромка не считается
  пересечением.

## 2. Разводка коллинеарных наложений (`internal/geom/lanes.go`)

### 2.1 `OffsetLanes(paths, obstacles, gap)`

Пути идут **в порядке отрисовки**: поздний подстраивается под ранние.

- Если внутренний сегмент очередного пути коллинеарен сегменту более раннего
  пути и перекрывается с ним больше чем на `gap`, сегмент уводится на `gap`
  в сторону.
- Не двигаются концы путей и сегменты, примыкающие к пинам: два линка в один
  пин должны сходиться, а не расходиться (`TestOffsetLanesKeepsPinJunction`).
  Поэтому перебираются только индексы `1 … len-3`.
- Сдвиг выбирается детерминированно: сначала `+gap`, при равном результате —
  вариант с меньшим суммарным наложением на уже разведённые пути.
- Сдвиг запрещён, если он режет блок, делает соседний сегмент нулевым или
  разворачивает его. Тогда сегмент остаётся на месте: **наложение лучше разреза
  блока**.
- До 6 проходов по пути; после каждого успешного сдвига сканирование начинается
  заново (путь изменился).

`obstacles[i]` — прямоугольники, внутренность которых путь `i` не должен резать
после сдвига (блоки; зоны пинов можно передавать уже расширенными).

### 2.2 `shiftLane`

Пробует `±gap` для сегмента `path[j]→path[j+1]`. Требования к соседям: они
должны быть перпендикулярны сдвигаемому сегменту (иначе сдвиг разорвёт путь) и
не должны схлопнуться или развернуться (`|a-prev| > |d| + eps` и симметрично для
`b-next`). Побеждает вариант с минимальной длиной коллинеарных перекрытий.

### 2.3 Вспомогательные

`collinearOverlapLen` — длина общего участка двух коллинеарных осевых отрезков;
`segHitsRect` — заходит ли сегмент внутрь прямоугольника (кромка не считается,
как и в `SegCrossRect`); `overlapLen` — суммарное перекрытие с более ранними
путями.

## 3. Маршрут как кривая и T-соединения (`internal/geom/path.go`, `internal/core/tap.go`)

### 3.1 Доля длины пути

- `PathLen` — манхэттенская длина ломаной (маршруты ортогональны).
- `PathAt(pts, t)` — точка на доле `t` (0..1) и единичное направление сегмента;
  `t` вне диапазона прижимается к концам, вырожденные сегменты пропускаются.
  Ось-выровненность не проверяется: редактор строит только ортогональные
  маршруты, но формула от этого не зависит.
- `PathFraction(pts, p)` — обратная операция: ближайшая к точке `p` доля длины и
  расстояние до пути (точка может быть мимо).
- `SegPointDist` — расстояние от точки до осевого отрезка и доля `f` (0..1)
  ближайшей точки вдоль него; для неортогональных отрезков работает по проекции.

### 3.2 Хранение T-соединения

Конец провода может упираться не в пин, а в точку на уже существующем проводе
(идея 1.3, открытый вопрос О1 §4.6). `TapLink{From, Tap{Host, T}}`:

- `Host` — ключ линка-хозяина в каноническом виде `From → To` (`LinkKey`);
- `T` — доля длины маршрута хозяина 0..1. **Координаты не хранятся**: при
  перестройке маршрута точка остаётся на своей доле пути, поэтому T-соединение
  живёт при любом сдвиге блоков.
- Отдельный список `Document.Taps`, а не поле в `Link`: `Link` остаётся
  сравнимым значением (история, буфер, дедупликация), а JSON v1 расширяется
  необязательным полем `taps` — старые файлы остаются валидными.
- Семантика §4.3: пин > junction > провод, идущий мимо. T-соединение — junction
  на сегменте: топология сводит линк с хозяином в одну группу, отрисовка ставит
  в точке оранжевый маркер как у пина с 3+ линками.
- Валидность: доля 0..1 (`FractionValid`), хозяин существует, хозяин не идёт из
  того же пина (иначе это нулевая дуга).

`LinkByKey`/`LinkIndex` — линейный поиск по ключу: документы этапа 1 маленькие.
`TapHostOf` возвращает хозяина T-соединения пина (пустая строка — нет).

## 4. Разрешение перекрытий блоков (`internal/core/overlap.go`)

**Инвариант редактора:** после любой мутации (drop, вставка, paste, align,
load) блоки не пересекаются. Правило §1: «перекрытия объектов ведут к
перерасположению их рядом».

### 4.1 `PushOverlaps(d, protected, grid, passes)`

1. Попарный обход `i < j`; при пересечении выбирается, кого двигать.
2. `protected` — блоки, которые не двигаются вообще (например, выделение при
   сбросе чужого блока). Если защищены оба — пара пропускается.
3. Если за `passes` проходов изменений не было — готово (`true`).
4. Проходов не хватило (плотная сцена, цепочка) — **страховка**: подвижный блок
   ставится в ближайшую свободную точку сетки (`freeSpot`). Позиция свободна от
   **всех** остальных блоков, поэтому новых наложений не создаёт.
5. Возврат — `!HasOverlaps(d)`.
6. `grid <= 0` принудительно заменяется на `1`: иначе `freeSpot` зациклится.

В приложении (`cmd/shbuilder`) первая попытка — только незащищённые блоки,
вторая — все: инвариант «блоки не пересекаются» важнее защиты выделения.

### 4.2 `push(mover, other, grid)`

- Считаются перекрытия по обеим осям; двигаем по оси **наименьшего** перекрытия.
- Сторона — по сравнению центров: если центр `mover` левее/выше, он уезжает
  влево/вверх, иначе вправо/вниз, вставая **рядом** с соответствующим краем
  `other`.
- Позиция снапится **наружу** (`snapOutward`): обычный `Snap` мог бы вернуть
  блок внутрь `other`.
- Страховка: если после снапа пересечение осталось, до 4 шагов по сетке в ту же
  сторону.

### 4.3 `freeSpot(d, m, grid)`

Кольца `k = 0…512` вокруг снапнутой текущей позиции. Внутри кольца
`max(|dx|,|dy|) == k` перебираются смещения в клетках сетки; выбирается
минимальное `dx²+dy²` (ничьи — по порядку обхода, то есть детерминированно).
512 колец с запасом покрывают любую сцену этапа 1.

`moverPair` детерминирован: если оба не защищены, двигается `b` (правый индекс).

## 5. История undo/redo (`internal/core/history.go`)

### 5.1 Почему снимки, а не Command

ADR-0004: операции этапа 1 составные и неделимые (drag + snap + push-apart) и
полностью исчерпываются состоянием; документы маленькие. Командный паттерн
(`command.go` из §13.3) вернётся на этапах 2+, когда появятся операции с большим
состоянием. Снимок — неизменяемая копия `Snapshot{Blocks, Links, Seq}`; блоки
копируются по значению.

### 5.2 Границы операций

- `Capture` — **до** мутации (по нажатию): кладёт снимок в undo-стек, ставит
  `pending`. Redo при этом не чистится: пользователь мог просто кликнуть.
- `Finish` — после отпускания/мутации клавишей: сравнивает `pending` с текущим
  состоянием. Если не изменилось — ничего не коммитит (холостой клик не
  захламляет историю). Если изменилось — умирает redo-будущее (стандартная
  семантика undo).
- `Undo`/`Redo` лениво счищают с верха стека состояния, равные текущему
  (холостые нажатия), затем загружают предыдущее и переносят текущее в
  противоположный стек.
- `Reset` — на старте и после загрузки файла: текущее состояние становится
  точкой отсчёта.
- `maxUndoDepth = 200` на каждый стек; `Depth()` — для HUD.

`LoadState` копирует снимок внутрь документа, поэтому загруженное состояние
нельзя испортить через `History`.

## 6. Упорядочивание выделения (`internal/core/arrange.go`)

Roadmap §13.3, пункт 1.4. Работают только по выбранным ID; `grid = 0` — без
привязки к сетке. Перед выбором референса блоки сортируются, чтобы порядок
обхода `map` в UI не влиял на результат; при равных координатах — по ID.

- **Align lefts/tops** — к крайнему (`min`), **rights/bottoms** — к крайнему
  (`max`); выравнивание идёт по рамке выделения, а не по среднему.
- **Align centers X/Y** — к **среднему центров** (общая ось симметрии); порядок
  не важен, потому что считается сумма.
- **Distribute X/Y** — крайние блоки не двигаются, шаг между центрами
  `(c1-c0)/(n-1)`; меньше трёх блоков — no-op.
- Позиция после снапа считается от центра/края: `b.X = target - b.W/2` и т.п.
- Выравнивание может свести блоки друг на друга, поэтому приложение сразу
  вызывает `PushOverlaps` (`TestArrangeNoOverlaps`).

## 7. Топология линков (`internal/core/topology.go`)

Union-find по пинам; ключ пина — строка `блок.пин` (`Endpoint.String`).
`find` сжимает путь, `union(a,b)` подвешивает `a` к `b`.

- `LinkGroups` — кластеры пинов, соединённых линками (junction). Каждый кластер
  отсортирован по endpoint-ам, кластеры упорядочены по первому endpoint —
  результат детерминирован.
- `FreePins` — пины без единого линка.
- `PinGroup` — группа конкретного пина (1 = свободный/одиночный).
- `OverlapsOf`, `Bounds` — вспомогательные для UI и будущей авто-рамки.

## 8. Формат файла (`internal/core/save.go`)

JSON schema v1 в конверте `{schema, blocks, links, taps?}` (ADR-0005,
`ideas.md` §7): человекочитаемо, git-дружелюбно, с версией схемы.
Реализовано как `MarshalJSON`/`UnmarshalJSON` у `Document` — обычный
`json.Marshal`/`Unmarshal` работает без обёрток.

- **Загрузка атомарна:** сначала разбирается `fileV1`, проверяется версия,
  строится новый `Document`, валидируется — и только потом заменяет текущий
  (`*d = *nd`). Битая схема, висячие линки, дубликаты ID, невалидные taps
  отвергаются, документ не портится (`TestLoadAtomic`).
- `Validate`: уникальные непустые ID, `pins ≥ 0`, `W,H ≥ 1`, все endpoints
  живые, у taps — доля 0..1 и существующий хозяин не из того же пина.
- `nextSeq` продолжает автонумерацию `bN` с максимума существующих ID, поэтому
  новые блоки не сталкиваются с загруженными.
- `taps` — необязательное поле: файлы без него валидны, схема остаётся v1
  (расширение, не ломающее изменение).
- `RemoveBlock` удаляет блок и все его линки и обрезает backing-массив
  (`links[:len:len]`), чтобы хвост не удерживался в памяти.

## 9. Канва: ввод и отрисовка (`cmd/shbuilder/main.go`)

### 9.1 Порядок отрисовки линков (П10)

Линки сортируются по `compareLinks`: сначала блок/пин начала, затем конца.
Порядок **не зависит** от последовательности создания, поэтому «кто прыгает
мостиком» не меняется между сессиями и запусками
(`TestLinkDrawOrderStable`, `TestRoutePipelineDeterministic`).

### 9.2 Мостики на пересечениях

Пересечения разных проводников на одной плоскости рисуются «аркой»: поздний
линк перепрыгивает ранний, ранние идут сплошными.

- Для каждого сегмента собираются параметры `t` пересечений с более ранними
  линками (проекция точки пересечения на сегмент в экранных координатах).
- Параметры сортируются; арка — `ArcTo` с равными фокусами, то есть
  полуокружность с центром в точке пересечения, радиус `arcR * zoom`.
- Слишком короткий сегмент (`length < 1` или `2r ≥ length`) и слишком тесное
  место у края (`tp - r ≤ pass` или `tp + r ≥ length`) рисуются сплошняком —
  иначе арки наезжали бы друг на друга.

### 9.3 Препятствия линка и полосы

- `linkObstacles(d, from, to)` — для `RouteEx`: чужие блоки с `Gap = outset`,
  собственные блоки концов с `Gap = 0` (иначе «флажок»), чужие пины — точки с
  `Gap = pinGap` (`TestLinkObstaclesForeignPins`).
- `laneRects(d, from, to)` — для `OffsetLanes`: блоки и квадраты `±pinGap`
  вокруг чужих пинов. Свои пины линка не мешают — путь из них выходит.
- `RouteAvoid` (блочный вариант) остаётся для тестов и простых вызовов;
  приложение использует `RouteEx` напрямую.

### 9.4 `rubberRoute` — предпросмотр резинки

Выход вдоль нормали пина (точка `e1` за габаритом):

- курсор «вперёд» по нормали — обычное колено (одна промежуточная точка);
- курсор «назад» — обход по каналу за торцом блока, чтобы провод не перерезал
  блок. Для горизонтального выхода канал — `min.Y - out` или `max.Y + out` по
  тому, к какому краю курсор ближе; для вертикального — `min.X - out` /
  `max.X + out`. Если вертикаль на `e1.X` блок не режет, обход не нужен.

### 9.5 Ввод, палитра, мини-карта

- Палитра слева (`paletteW = 132 px`) — 6 строк (блок с 1..6 пинами);
  клик ставит блок в центр видимой канвы, а не под курсор-палитру. Пока идёт
  драг/линк/панорама, события над палитрой не перехватываются, иначе драг
  «залипнет».
- Приоритет попадания: пин → блок → пустое (рамка выделения).
- Сброс блока: snap к текущей сетке + `PushOverlaps` («рядом», §1).
- Скролл на Windows присылает большие дельты (±120 за тик) — берётся только
  знак: один тик = 5 % зума.
- Мини-карта вместо скроллбаров: уменьшенная схема + рамка видимой области;
  клик переносит зону видимости; `Home` — вся схема в окне (`fitToWindow`,
  палитра отнимает полосу); стрелки — пан.

### 9.6 Клавиатура и фокус (тройная страховка)

Клавиши работают только при выполнении **всех трёх** условий:

1. `event.Op(gtx.Ops, keyTag)` — иначе у handler'а нет `visible`;
2. `key.FocusFilter{Target: keyTag}` — ради жизненного цикла фокуса: без него
   `keyQueue.Frame()` в конце кадра снимает фокус;
3. `key.FocusCmd{Tag: keyTag}` — собственно фокус.

`key.Filter{}.Optional` обязан перечислять **все** модификаторы:
`keyFilterMatch` отбрасывает событие при `e.Modifiers &^ (Required|Optional) != 0`,
поэтому без этого Ctrl+Z, Shift+стрелки и т.п. не доходили бы до `handleKeys`
(`TestKeyDeliveryHeadless`). Ctrl — `key.ModShortcut` (на Windows Ctrl, на mac Cmd).

### 9.7 Камера, зум, сетка

- Мир = 1 мм; `screen = world*zoom + pan`; «100 %» = 4 px/мм (`pxPerMM`).
- `ZoomMin = 0.4`, `ZoomMax = 32` px/мм (10 %…800 %). Прежние 0.1–8
  «px-домена» давали 2.5 %…200 %: сцена схлопывалась в точку и «уезжала»
  (отзыв от прогона) — поэтому границы заданы в px/мм.
- `ZoomAt` держит мировую точку под курсором на месте:
  `zoom *= factor`, `pan = screen - world*zoom`.
- Сетка: 5 / 10 / 20 мм, цикл по `G` (умолчание 10 мм), `geom.Snap` —
  округление к ближайшему кратному.

## 10. Сводка инвариантов

1. `Hairpins(route) == 0` — ни одного крюка (разворота на 180° тем же `x`/`y`).
2. Блоки не пересекаются после любой мутации; `PushOverlaps` — точка входа.
3. Маршрут начинается и кончается в пинах; `OffsetLanes` не двигает концы и
   подходы к общим пинам.
4. Порядок отрисовки линков детерминирован (ключ линка, не порядок создания).
5. Undo не возвращает наложения: загрузка разводит перекрытия **до** снимка.
6. Загрузка файла атомарна: невалидный файл не меняет документ.
7. Все координаты блоков после мутаций снапятся к текущей сетке (5/10/20 мм).
8. `RouteOpts.Prev` влияет только на выбор стороны обхода, не на геометрию.
