# problems.md — журнал проблем (сценарные прогоны)

Одна проблема = одна запись с четырьмя блоками:

- **Проблема** — что видел/сформулировал пользователь.
- **Что найдено** — причина в коде/данных, подтверждённая фактами (воспроизведение, замеры).
- **Что сделано** — фикс, тесты, документация, коммиты.
- **Что предлагается** — что осталось решить/проверить.

Статусы: `открыта` → `исправлена, ждёт проверки` → `закрыта`.
Приёмка правки: `go build ./... && go test ./... && go vet ./...` — зелёные,
дифф не удаляет существующие функции (см. ПР-3).

## ПР-1. «Крюк» в трассировке соединительной линии

**Дата:** 2026-11-06 · **Статус:** исправлена, ждёт проверки пользователем ·
**Слой:** `internal/geom` (маршрутизация) → отрисовка линков

### Проблема

Линия идёт горизонтально, затем уходит вниз вертикально, там меняет
направление вверх с сохранением x, поднимается и только потом идёт
горизонтально как требуется. Визуально — «странный крюк», разворот на 180°
на ровном месте. На сцене пользователя: 2 крюка в первом прогоне, 3 — во
втором. Ожидание: линия нигде не идёт назад по своей оси.

### Что найдено

1. **Причина — жёсткое правило в `geom.detourAround`.** Обход препятствия
   всегда возвращался на исходную линию `y` у точки `b`, даже когда
   продолжение маршрута после `b` идёт в обратную сторону. Получался цикл
   «вниз → вверх тем же x»:

   ```
   было:  (35,-30) → (-85,-30) → (-85,-45) → (-85,-30) → (-85,-70)
                                  обход сверху   ^^^^^^^ возврат вниз,
                                                            а дальше снова вверх
   ```

2. **Второй дефект, найденный перебором: зацикливание обхода.** Маршрут
   повторял петли-«лепестки» до лимита итераций (10), т.е. линия могла
   вырастать до десятков точек. Причина: повторный обход того же препятствия
   в той же точке входа; вырожденный обход (`detourY == y`, `enterX == a.X`)
   считался успешным и не менял маршрут.

3. **Масштаб.** Перебор конфигураций (свой блок + чужой блок + цель, шаг
   10 мм): **315 711** маршрутов с крюком; из них коротких (≤12 точек) —
   **144 933**; плюс маршруты-петли до лимита итераций.

4. **Почему не поймали раньше.** Тесты проверяли «не режет блок» и «зазор
   5 мм», но не форму линии. `Clean` намеренно сохраняет развороты
   (hairpin), поэтому крюк доживал до отрисовки.

### Что сделано

1. `detourAround` больше не следует одному правилу: строит **кандидатов**
   (обход с двух сторон; с возвратом на линию и без возврата, когда
   следующий сегмент коллинеарен продолжению) и выбирает по оценке
   «нет разворотов → короче».
2. Точка входа в зону не откатывается назад по ходу движения
   (`enterX`/`enterY` clamp).
3. Защита от петель: множество `seen` (препятствие + точка входа),
   вырожденный обход не засчитывается (`samePath`), лимит детуров 64.
4. Новый контракт `geom.Hairpins(route) == 0` — число разворотов в ломаной.
5. Тесты: `TestRouteAvoidNoHooks` (точные конфигурации из отзыва + перебор
   ~142 тыс. маршрутов) и `TestDemoLinksNoHooks`. Проверено, что на старом
   коде тест падает ровно на обеих конфигурациях из отзыва (`крюков 1`).
6. Документация: свод правил трассировки — `ideas.md` §4.6, gotcha — `AGENTS.md`.
7. **Результат после фикса:** 142 360 маршрутов — 0 крюков, 0 петель,
   максимум 12 точек; `go build ./... && go test ./... && go vet ./...` —
   зелёные; smoke-прогон `shbuilder.exe` — живой.
8. **Перебор расширен на несколько препятствий** (пункт «что предлагается»
   из первой редакции): `TestRouteAvoidTwoObstacles` — 287 776 маршрутов,
   `TestRouteAvoidThreeObstacles` — 45 136 маршрутов. Проверяются П4 (нет
   крюков), П5 (нет петель), П6 (зазор ≥ 5 мм до каждого чужого блока) и
   совпадение концов с пинами — нарушений нет.
9. **Мультилинковая сцена и порядок отрисовки:** `TestManyLinksNoHooks`
   (6 линков, 3 пересечения — без крюков, петель и разрезов блоков);
   `TestLinkDrawOrderStable`. В `drawLinks` порядок теперь по ключу линка
   (`compareLinks`), а не по порядку создания, — мостики детерминированы
   (П10), одинаковая схема рисуется одинаково в любой сессии.

Коммиты: `9a05559` (фикс + тесты), `d2599bf` (свод правил).

### Что предлагается

1. **Пользователю:** перепроверить ту же сцену и те же 2–3 места — крюков
   быть не должно.
2. **Решения по О1–О3 приняты (2026-11-07):** наложения разводить сдвигом
   (П12), чужие пины обходить (П11), гистерезис стороны включить (П13).
   Реализовано — см. ПР-4. Открытыми остались О1 (T-соединение в середину
   провода) и О2 (шины).
3. **Мультилинковая сцена:** расширена до 8 линков с намеренными
   наложениями — `TestEightLinksLanes` (см. ПР-4, п. 6): наложений длиннее
   `laneGap` не осталось, все пути заканчиваются в своих пинах. Базовая
   сцена 6 линков / 3 пересечения — `TestManyLinksNoHooks`.

## ПР-2. Отладочная строка «клав:» в HUD

**Дата:** 2026-11-06 · **Статус:** закрыта ·
**Слой:** `cmd/shbuilder` (отрисовка HUD)

### Проблема

В HUD постоянно висела строка `клав: <последняя клавиша>`, добавленная при
починке доставки клавиатуры. Пользователю она не нужна и занимает место.

### Что найдено

`drawHUD` печатал `ed.lastKey`. Само поле нужно только headless-тесту
`TestKeyDeliveryHeadless` — он проверяет, что `Ctrl+G` дошёл до обработчика
(без этого теста регресс клавиатуры снова стал бы невидимым).

### Что сделано

- Удалён блок вывода `клав:` из `drawHUD` (три строки; HUD стал короче).
- Поле `lastKey` и его заполнение **сохранены** как тестовый хук
  (комментарии у поля и присваивания это фиксируют).
- `go build ./... && go test ./... && go vet ./...` — зелёные.

### Что предлагается

Если диагностика ввода снова понадобится — возвращать её под флаг
(debug/verbose), а не постоянно в HUD.

## ПР-3. Правки параллельного агента сломали сборку и потеряли функции

**Дата:** 2026-11-06 · **Статус:** закрыта (откат) ·
**Слой:** `cmd/shbuilder`, `internal/geom`, документация

### Проблема

После работы другого агента `go build ./...` падает, а редактор растерял
функции. Коммитов агент не делал — правки лежали в рабочем дереве.

### Что найдено

1. **`cmd/shbuilder/main.go` заменён на 533 строки вместо 1106.** Пропали
   `demoScene`, `drawGrid`, `drawMiniMap`, `drawBlocks`, `drawPins`,
   `drawSelBox`, `drawRubber`, `arrangeKey`, `pasteClip`, `undoMark`,
   `redoMark` — т.е. демо-сцена, сетка, мини-карта, отрисовка блоков/пинов,
   выделение рамкой, выравнивание, буфер и undo/redo. В `package main`
   заведены собственные `Vec`/`nearf`/`eps` поверх `geom`. Синтаксическая
   ошибка: `main.go:174 unexpected name app`.
2. **`internal/geom/geom.go`.** В конец рабочего файла вклеен комментарий
   теста («TestKeyDeliveryHeadless — хоть бы один тест прогонал без GUI»),
   добавлены `ArcParams`/`endpointKey`, испорчены существующие комментарии
   (`не knows`, `осе-выровненным`, `растущий`).
3. **`problems.md`** переписан в свободной форме — формат
   «Проблема / Что найдено / Что сделано / Что предлагается» потерян,
   запись про крюк исчезла.
4. **Идея** `ArcParams` (радиус арки в мм, подавление коротких арок,
   детерминированный порядок линков) разумна, но реализация нерабочая.

### Что сделано

- `git checkout` четырёх файлов (`main.go`, `geom.go`, `geom_test.go`,
  `problems.md`) — восстановлено последнее зелёное состояние.
- Из идей агента оставлено только полезное и безопасное: снятие `клав:`
  из HUD (см. ПР-2).
- `ArcParams`/`endpointKey` не приняты (нерабочие, ломают сборку).
- Журнал возвращён к прежнему формату, добавлены ПР-2 и эта запись.
- Проверено: `go build ./... && go test ./... && go vet ./...` — exit 0.

### Что предлагается

1. **Если нужна мировая arc-логика** — сделать заново на текущем
   `drawLinks`: стабильный ключ сортировки линков, радиус арки в мм,
   suppress-правила (короткий сегмент, близость к концу), отдельным
   коммитом с тестами. Сейчас арки уже работают (`arcR = 1.6` мм,
   `TestArcStrokeHeadless`), но порядок отрисовки — по порядку линков
   в документе; это можно улучшить детерминированной сортировкой.
2. **Правило приёмки правок** (в т.ч. от других агентов): сборка, тесты и
   vet зелёные; в диффе нет массовых удалений (`--stat`), нет замены файлов
   целиком без причины; кодировка и комментарии не портятся.

## ПР-4. Три решения по трассировке: наложения, чужие пины, гистерезис

**Дата:** 2026-11-07 · **Статус:** исправлена, ждёт проверки пользователем ·
**Слой:** `internal/geom` (RouteEx/OffsetLanes) → `cmd/shbuilder` (drawLinks)

### Проблема

После разбора ПР-1 остались три открытых вопроса §4.6; пользователь выбрал:
(1) коллинеарные наложения линий разводить сдвигом 2 мм, (2) чужие пины
обходить, (3) сторону обхода не менять от микросдвига блока (гистерезис).

### Что найдено

1. **Наложение.** Маршруты двух линков, идущие по одной линии, рисовались
   поверх друг друга — визуально один провод, хотя это два разных соединения.
   Геометрия линка не хранится (П9), поэтому разводить нужно на отрисовке.
2. **Чужой пин.** Пин — точка на кромке блока; для чужих блоков действует
   зона 5 мм, но для *своих* блоков линка зоны нет (П7), и провод мог пройти
   ровно через другой пин того же блока — выглядело как подключение.
3. **Перескок стороны.** При симметричном обходе (равные варианты сверху и
   снизу) выбор делался по порядку кандидатов; сдвиг блока на доли мм менял
   сторону, линия «прыгала» на другую сторону блока.

### Что сделано

1. **`geom.Obstacle{Rect, Gap}` + `geom.RouteOpts{Obstacles, Prev, Sticky}` +
   `geom.RouteEx`.** `RouteAvoid` оставлен обёрткой (обратная совместимость
   тестов и вызовов). Зазор теперь у каждого препятствия свой: `Gap == 0` —
   только «не резать» (свои блоки), точка с `Gap` — пин.
2. **`geom.OffsetLanes(paths, obstacles, gap)`** — разводка наложений:
   пути в порядке отрисовки; внутренний сегмент, лежащий на линии раннего,
   уводится на `gap`. Концы и сегменты у пинов не двигаются (линки в общий
   пин сходятся); при упоре в блок сдвиг идёт в другую сторону, иначе
   остаётся наложение. Направление и результат детерминированы.
3. **Гистерезис в `detourAround`:** если вариант не длиннее лучшего больше
   чем на `sticky`, выбирается ближайший к `Prev` (манхэттенское расстояние
   до вершин прошлого маршрута). Память — `editor.lastRoutes` по ключу
   `from->to`, обновляется каждый кадр.
4. **`cmd/shbuilder`:** `linkObstacles` (блоки + все пины, кроме концов),
   `laneRects` (блоки и зоны пинов для проверки сдвига), конвейер
   `drawLinks`: маршрут → сортировка по ключу → `OffsetLanes` → арки.
   Резинка при наведении на пин использует те же препятствия.
5. **Константы:** `pinGap = 2` мм, `laneGap = 2` мм, `stickyMM = 3` мм.
6. **Тесты:** `TestRouteAvoidForeignPin`, `TestDetourSideSticky`,
   `TestOffsetLanesSeparatesOverlaps/KeepsPinJunction/AvoidsBlock`,
   `TestLinkObstaclesForeignPins`, `TestDemoProductionRoutes`,
   `TestRoutePipelineDeterministic` (независимость от порядка создания),
   `TestEightLinksLanes` (8 линков, 8 пересечений: наложений длиннее
   `laneGap` не осталось, все пути в своих пинах).
7. **Проверка:** `gofmt` чисто, `go build ./... && go test ./... && go vet ./...`
   — зелёные; `shbuilder.exe` собран, smoke-прогон 4 с — живой.

### Что предлагается

1. **Пользователю:** проверить на своей сцене — наложения разведены,
   провод не проходит через пины, при микросдвиге блока сторона обхода
   не перескакивает.
2. **Открытыми остались** О1 (T-соединение в середину провода) и О2 (шины);
   правила П11–П13 зафиксированы в `ideas.md` §4.6.
3. **Если 2 мм разводки мало/много** — это одна константа `laneGap`
   (и `pinGap` для пинов), менять без переделки алгоритма.

## ПР-5. Блоки добавлялись только хоткеями — нет палитры

**Дата:** 2026-11-07 · **Статус:** исправлена, ждёт проверки пользователем ·
**Слой:** `cmd/shbuilder` (палитра, ввод, HUD) + `ideas.md`

### Проблема

В этапе 1 блоки добавлялись только клавишами `1..6` — наглядного выбора
«какой блок с каким числом пинов» не было (roadmap §13.3, п. 1.1: палитра
слева не начата). Плюс при курсоре у левого края окна хоткей мог поставить
блок за пределами видимой канвы, и блок «терялся».

### Что найдено

1. `addPinBlock` брал `ed.cursor` без проверки, что точка над канвой: при
   курсоре у левой/верхней кромки блок уезжал за видимую часть.
2. В `handleInput` не было полосы, перехватывающей клики левее канвы: любой
   клик уходил в пан/выделение/создание линка.
3. HUD (`drawHUDLine`) и `fitToWindow` считали канвой всё окно — после
   появления панели текст и «вся схема» заезжали бы под неё.

### Что сделано

1. `drawPalette`: полоса `paletteW = 132 px`, заголовок «Палитра / клик или
   1..6», 6 строк по 46 px. В строке — мини-блок 38×26 px с пинами по
   `core.PinLayout`, подпись «N пин/пина/пинов» (`pinWord`) и подсветка под
   курсором.
2. `paletteRowRect` / `paletteHit` / `inPalette` + ранняя ветка в
   `handleInput`: клик по строке вызывает `addPinBlockAt` в точке
   `canvasInsertScreen` (центр видимой канвы), блок сразу выделяется;
   палитра не отдаёт канве клики и колесо, пока не идёт драг/линк/панорама.
3. `canvasInsertScreen`: курсор над канвой — вставка под курсором; над
   палитрой или вне окна — центр видимой канвы (хоткей `1..6` ведёт себя
   так же).
4. `addPinBlock` разделён на обёртку и `addPinBlockAt` — общий undo-шаг
   (Capture/Finish), push-apart и dirty-флаг.
5. `fitToWindow` и HUD учитывают `paletteW`: схема центрируется в видимой
   канве, строки HUD сдвинуты правее палитры.
6. Тесты: `TestPaletteHit`, `TestPinWord`, `TestPaletteInsertCenter`
   (центр канвы, n пинов, undo-шаг, вставка под курсором); обновлён
   `TestFitToWindow` (центр видимой канвы).
7. Проверка: `gofmt`, `go build ./... && go test ./... && go vet ./...` —
   зелёные; smoke-прогон: палитра видна, клик по строке поставил `b1` в
   центр канвы, блок выделен.

### Что предлагается

1. **Пользователю:** проверить на своей сцене — клик по строкам 1..6 ставит
   блок в центр канвы, хоткей над палитрой не «теряет» блок.
2. Ширина палитры — одна константа `paletteW`; если мешает на узком окне,
   сделать складываемой (кнопка/хоткей) — пока не делали.
3. На этапе 2 палитра должна генерироваться из метаданных домена
   (§3 `ideas.md`: библиотека элементов + инспектор); сейчас это заготовки
   блоков с 1..6 пинами.

## ПР-6. Блоки накладывались и пересекались между собой

**Дата:** 2026-11-07 · **Статус:** исправлена, ждёт проверки пользователем ·
**Слой:** `internal/core` (overlap) → `cmd/shbuilder` (arrange/drop/insert/load)

### Проблема

Пользователь: «блоки не могут накладываться, пересекаться». Вердикт редактора
§1: перекрытия объектов ведут к перерасположению их рядом. Нарушение найдено:
`arrangeKey` не расталкивал блоки после align/distribute; даже при отказе
`PushOverlaps` не разрешал остаточные наложения принудительно.

### Что найдено

1. **`arrangeKey` (A/R/T/B/H/V/D):** align/distribute двигали блоки по
   выравниванию, но push-apart не вызывался — блоки оставались сведёнными
   (на демо-сцене: `V` по центрам сделала Y равным, и пары A/C и B/D совпали).
2. **`PushOverlaps`:** после исчерпания `passes` финальная проверка молча
   возвращала `false`, без принудительного разрешения.
3. **Загрузка:** файл с перекрытиями принимался как есть.

### Что сделано

1. `core.PushOverlaps` — принудительный fallback: остаточные пересечения
   разрешаются через `freeSpot` (ближайшая свободная клетка сетки); возвращает
   true, только когда `HasOverlaps == false`.
2. `core.HasOverlaps` — единая проверка наложений.
3. Границы мутаций, где инвариант «блоки не пересекаются» гарантируется:
   drop (drag-release) и вставка/paste через final check, `arrangeKey` — после
   любого align/distribute; `loadDoc`/`newApp` — развод при загрузке.
4. Тесты: `internal/core` (`HasOverlaps`, плотная сцена, fallback-цепочка),
   `cmd/shbuilder` (arrange/drop/вставка — без наложений).

### Что предлагается

1. **Пользователю:** проверить на своей сцене — align/distribute (T/H/V/D), drag
