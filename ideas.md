# Mозговой штурм: Редактор схем и симулятор цепей (AC/DC) на Go, desktop

> Документ подготовлен для передачи другим моделям/аналитикам. Структура: постановка →
> варианты технологий → архитектура → алгоритмы → симуляция → этапы → риски → открытые вопросы.
>
> Контекст: автор в школьные годы писал подобное приложение на Паскале/Delphi (код утерян).
> Хотелось бы воспроизвести функционал: редактор схем (перетаскивание элементов, проводники,
> перестроение топологии и перерисовка «на лету») + моделирование процессов в цепях
> постоянного и переменного тока.

---

## 1. Постановка задачи: два этапа (принято владельцем)

Ключевое решение: **физика и математические модели — только на втором этапе.**
Первый этап — чистый графический редактор диаграмм «блоки + коннекторы».

### Этап 1 — Редактор (без физики)

Что должно уметь приложение:
- Палитра блоков; блок = графический символ + подпись (+ произвольные строковые
  поля). Никакой электрической/физической семантики на этом этапе нет.
- Размещение drag & drop, перемещение, вращение, удаление, копирование, группы.
- Соединение блоков коннекторами (проводами) между точками входа/выхода.
- **Живая перерисовка коннекторов** при перемещении блоков: rubber-band во время
  drag, автодоколка и перестройка ортогонального маршрута после отпускания.
- **Обработка пересечений коннекторов:** пересечение ≠ соединение — связь
  создаёт только явный junction/пин; визуальная индикация касаний, приоритеты
  определения контактов (пин > junction > мимо идущий провод, §4.3, риск 5 §9).
- **Упорядочивание элементов:** snap к сетке, выравнивание (align), распределение
  (distribute), растягивание, порядок слоёв, раскладка по уровню/дереву (для
  mind map — tidy/radial layout; для схем — опционально).
- Зум/панорамирование, undo/redo, буфер обмена, save/load (JSON).

Критерий готовности этапа 1: любую диаграмму/схему можно **нарисовать, разложить
и отредактировать** — и это уже полезный инструмент, независимо от симуляции.

### Этап 2 — Физическая привязка и мат. модели

- Типизация блоков: резистор, катушка, конденсатор, источники (DC/AC/импульс),
  земля, измерительные приборы; параметры с единицами измерения.
- Из геометрии коннекторов → топология сети (union-find) → netlist.
- Симулятор: DC operating point, transient (RC/LC/RL), AC-анализ; зонды и графики.
- Опционально позже: экспорт netlist в SPICE-совместимом формате.

**Не в MVP (но держать в голове):** нелинейные элементы (диод/транзистор),
Newton–Raphson, сложные нестационарные источники, совместимость с LTspice/ngspice,
3D, «сборка на печатной плате».

Связь с §1б: этап 1 — это и есть generic node-edge editor; электрическая схема
и mind map становятся «доменами», навешиваемыми поверх одного и того же редактора
(этап 2 для схем — как раз та самая «физическая привязка»).

## 1б. Обобщающая концепция: не только цепи — редактор графов (node-edge editor)

Ключевое наблюдение: **редактор схем и mind map — один и тот же продукт по ядру**:
канва с узлами и связями, drag, zoom/pan, hit-testing, undo/redo, сериализация,
перестройка связей «на лету». Отличается только «домен» — семантика узлов/рёбер
и то, что мы делаем с документом дальше.

### 1б.1 Что общего (переиспользуется на 100%)

- Камера (pan/zoom), трансформации, hit-test, выделение, marquee, snap/привязки.
- Документ: позиции, группы, буфер обмена, команды → undo/redo, версионирование JSON.
- Граф-ядро: узлы, рёбра, инкрементальный пересчёт связности при перетаскивании
  (union-find / spatial hash из §4.3 — работает для любого домена).
- Рендер-сцена: слои, подсветка hover/selected, «rubber-band» при перетаскивании.
- Фреймворк авто-раскладки (нужен mind map'у, полезен и для «красивой» схемы).

### 1б.2 Что домен-специфично

| Аспект | Circuit (электрика) | Mind map |
|---|---|---|
| Узлы | фиксированный символ + пины в точках | свободный текстовый блок, размер = содержимому |
| Рёбра | ортогональные проводники, геометрия хранится | кривые Безье parent→child, вычисляются из позиций |
| Топология | произвольный граф + «земля», циклы обязательны | строго дерево (иерархия), циклы — ошибка |
| Семантика | netlist → solver (§5), измерители, осциллографы | навигация: collapse/expand, поиск, ветки-теги |
| Авто-раскладка | не нужна (пользователь рисует) | обязательна (radial / tidy tree) |
| Экспорт | SPICE netlist, SVG | OPML, Markdown, PNG/SVG |
| Симуляция | ★ главная фича | отсутствует (или «прогресс-метафоры») |

Третьи домены, которые ядро обслуживает бесплатно: block diagram / signal flow,
flowchart, state machine, org chart, family tree, сетевые топологии.

### 1б.3 Стратегические варианты

- **A. Единое ядро + доменные пакеты (рекомендуется).** Минимальное generic-ядро
  (document/camera/commands/graph) + слой `domain/` с интерфейсом примерно:
  `Domain: NodeTypes() | Validate(doc) | Layout(doc) | Analyze?(doc) | SymbolRenderer(...)`.
  Палитра и инспектор генерируются из метаданных домена. Сначала MVP = **один** домен
  (выбрать), второй домен добавляется как плагин — и только тогда видно, ядро ли это
  или over-engineering.
- **B. Mind map — продукт, схемы «потом/никогда».** Быстрее до «пользовательской»
  ценности (нет solver'а), но теряется исходная цель — школьный симулятор цепей.
- **C. Схемы — продукт, mind map — будущее расширение.** Верно оригинальной амбиции;
  ядро с первого дня закладывать «доменно-нейтральным», но не строить второй домен,
  пока не готов первый.

### 1б.4 Влияние на архитектуру (§3)

```
internal/
  core/        # было model+render: позиции, команды, камера, документ (домен-нейтрально)
  graph/       # было topology: связность, union-find, валидация дерева/графа
  domain/
    circuit/   # пины, ортогональные провода, netlist, валидация «нет земли»
      sim/     # было simulate: MNA, DC/transient/AC  ← живёт ТОЛЬКО здесь
    mindmap/   # типы узлов, дерево, tidy/radial layout, collapse/expand
  ui/          # палитра/инспектор из метаданных домена
```

Правило против over-engineering: **ядро не знает про «электричество» и про «деревья»**;
оно знает про позиции, выделение, команды и граф. Абстракции выделять по факту
второго домена, а не заранее (но интерфейс `Domain` заложить с самого начала — он дёшев).

### 1б.5 Риски унификации

- **Слишком общее ядро** хуже обоим доменам (circuit требует жёстких пинов,
  mind map — свободного текста). Митигация: геометрию узла владеет домен,
  ядро владеет только позицией/размером бокса/выделением/камерой.
- **Рёбра:** у circuit геометрия — данные, у mind map — функция от позиций узлов.
  Хранить в ребре опциональное `geometry`; если нет — вычислять (единая модель).
- **Провод vs связь:** в circuit «висящий провод» — первоклассный объект,
  в mind map ребро никогда не «висит». Не пытаться сделать «висящие» общими.
- Правило большого пальца: MVP одного домена + заранее заложенный интерфейс `Domain`
  = лучший баланс; два домена сразу — только если есть силы на оба.

### 1б.6 Влияние на этапы (§8) и вопросы (§10)

- Этапность из §1 (сначала редактор, потом физика) идеально ложится на эту схему:
  этап 1 = generic-ядро, этап 2 = домен `circuit` с симуляцией; mind map —
  кандидат на домен №2 поверх того же ядра.
- Этап 0 (spike): один холст, на нём блоки + коннекторы — проверить, что ядро
  принимает разные типы узлов/рёбер без костылей.
- Открытые вопросы по доменам — в §10.

## 2. Главная развилка: чем рисовать UI в Go

### Вариант 1: Gio (github.com/eliukis/… — актуально: gioui.org) — immediate mode GUI
- **Плюсы:** весь UI и canvas в одном Immediate-mode рендере (OpenGL/Metal/Vulkan/DX12),
  очень производительный, идеально ложится на «свой» редактор схем, где 99% экрана —
  одна канва с собственной отрисовкой. Нет зависимости от нативных виджетов.
  Удобен для: трансформаций (zoom/pan), hit-testing, инкрементальной перерисовки.
- **Минусы:** своя система виджетов, кривая обучения, придётся самому писать
  панели/кнопки/диалоги (или использовать gioui-расширения). Меньше «нативности».
- **Вердикт:** ★ лучший кандидат для редактора, где всё — собственная графика.

### Вариант 2: Fyne (fyne.io)
- **Плюсы:** зрелый, кроссплатформенный, есть `canvas` (полилинии, прямоугольники,
  эллипсы, текст), свой scene-graph, легко делать приложения «с коробки» (меню, диалоги, настройки).
- **Минусы:** собственный renderer на OpenGL, производительность и качество
  векторной отрисовки при больших схемах/зуме хуже; сложнее тонко управлять
  инвалидацией областей; рендер-баги на некоторых GPU/Windows DPI.
- **Вердикт:** ★ разумный «быстрый старт», если не гнаться за плавностью 60 fps на сложных схемах.

### Вариант 3: Wails (webview) — Go-бэкенд + HTML/Canvas/SVG фронтенд
- **Плюсы:** редактор схем на SVG/Canvas — это, по сути, веб-фронтенд; богатый UI
  «бесплатно» (React/Svelte/Vue), быстрый прототип, отличные графики (Chart.js, d3),
  zoom/pan через CSS/SVG transforms.
- **Минусы:** уже не «чисто Go» (фронт на JS), большие схемы в SVG тормозят
  (решается canvas + ручной hit-test), упаковка бинарника с ассетами.
- **Вердикт:** ★★★ если готовить UI быстрее, чем бороться с GUI-библиотеками Go;
  симулятор и топология — в Go, отрисовка — на canvas.

### Вариант 4: Нативные обёртки
- **Walk** (Windows-only, Win32): нативный виджет-контрол, но канва всё равно своя
  (WM_PAINT/OwnerDraw). Плюс — «как в настоящем Windows-приложении»; минус — только Windows.
- **gotk4/gotk3 (GTK4/GTK3):** есть DrawingArea, но GTK на Windows — боль (зависимости, DPI).
- **Ebiten / raylib-go / SDL:** отличный 2D-рендер (game loop), но UI-кита нет —
  кнопки/меню/диалоги писать руками. Хорошо подходит, если главный кайф — «свой» рендер.
- **Вердикт:** только если нужна нативность Win32 (Walk) или максимальный контроль над рендером.

### Вариант 5: Гибрид «симулятор на Go, UI где угодно»
Go-библиотека/CLI-ядро (топология + solver) + любой UI поверх. Полезно для тестов,
бенчмарков и повторного использования (CLI-режим, серверный режим, плагин).

**Рекомендация (для обсуждения):** Gio (максимум контроля, всё в Go) **или** Wails
(максимум скорости разработки UI). Fyne — запасной вариант «побыстрее и попроще».

## 3. Архитектура приложения (независимо от GUI)

```
cmd/schemedit/          # точка входа, сборка GUI
internal/
  model/                # доменная модель (чистый Go, без GUI)
    component.go        # Component, Pin, типы элементов, параметры
    wire.go             # Wire (сегменты, точки), Junction
    schematic.go        # Schematic: коллекции, операции add/move/delete/rotate
    command.go          # Command pattern → undo/redo
    serialize.go        # JSON/SQLite, версии схемы
  topology/             # построение сети из геометрии
    graph.go            # узлы/рёбра, union-find слияние контактов
    netlist.go          # netlist: список ветвей (branch) для solver
  simulate/
    mna.go              # Modified Nodal Analysis solver (dense/sparse)
    models.go           # компаньон-модели R/L/C, источники
    dc.go               # operating point
    transient.go        # шаг по времени (трапеция/Бэквард Эйлера)
    ac.go               # комплексный малосигнальный анализ
    results.go          # кольцевые буферы сигналов для графиков
  render/               # (если Gio/Ebiten) отрисовка сцены, камера, хит-тест
  ui/                   # виджеты, панели, инспектор параметров, графики
  app/                  # wiring: события → команды → пересчёт → перерисовка
```

Ключевые принципы:
- **`model`, `topology`, `render`, `ui` живут на этапе 1**; пакет `simulate`
  появляется только на этапе 2+ (§8) — на этапе 1 его не проектировать «про запас».
- **`model` и `simulate` не знают о GUI** → тестируются юнит-тестами, переносятся в CLI.
- **На этапе 1 у блока нет физического типа** — только `Type` (иконка/палитра),
  позиция, подпись; поля `Value/AC` и netlist добавляются на этапе 2 (§4.1).
- **Иммутабельные операции через Command** (MoveComponent, AddWire, SetValue…) → undo/redo даром.
- **Единый источник истины — `Schematic`**; renderer — проекция модели в пиксели.
- Событийный цикл: input event → команда → инкрементальный пересчёт топологии →
  dirty-флаги (geometry/netlist/plots) → рендер только изменённого.

## 4. Модель данных и топология (самая «школьная» и самая важная часть)

> Этапность: геометрия/пины/пересчёт топологии (§4.1–4.4) — этап 1;
> физические поля (`Value`, `AC`) и netlist — этап 2 (см. §1, §8).

### 4.1 Элементы
```go
type Component struct {
    ID, Type     string      // "resistor", "voltage_source", ...
    Pos          Vec2        // точка «привязки» (центр)
    Rotation     int         // 0/90/180/270
    Value        float64     // Ом / Генри / Фарады / Вольты / Амперы
    AC           *ACSpec     // амплитуда, частота, фаза (для AC-анализа)
    Pins         []Pin       // локальные координаты контактов
}
```
Пины трансформируются через rotation+translation → мировые координаты.

### 4.2 Проводники
- Wire = ломаная из сегментов (или один сегмент). Хранить как список точек;
  при перетаскивании конца — перестроить ортогонально (auto-route: 1–2 колена).
- Точки касания: пин↔провод, провод↔провод (T-образные), «junction» (точка-сцепка).

### 4.3 Пересчёт топологии при перемещении (в «реальном времени»)
1. **Инкрементально:** при drag обновляются только узлы, связанные с двигаемым объектом
   (пространственный индекс: grid-hash или R-дерево по точкам).
2. **Union-Find (Disjoint Set):** каждая точка контакта объединяет узлы; компоненты
   связности = электрические узлы сети (net). O(α(n)) — мгновенно.
3. **Дебаунс/фазы:** во время drag — только геометрия и подсветка «висящих» концов;
   netlist пересобирается на mouse-up (или раз в N мс), чтобы не дёргать solver.
4. **Отрисовка:** «висящие» провода следуют за пином (rubber-band), после отпускания —
   автодоколка до ближайшего пина/сетки.

### 4.4 Hit-testing
- Сначала быстрый grid-hash (ячейка ~ размер компонента), потом точный тест
  (дистанция до сегмента < порога, учёт толщины линии и масштаба).
- Состояния hover/selected/being-dragged — слои подсветки.

### 4.5 Разводка проводников
- MVP: ортогональные провода вручную (пользователь ведёт мышью, snap к сетке).
- Позже: авто-разводка A*/Lee по сетке с обходом существующих проводов и элементов,
  роутинг «по диагонали запрещён», стоимость = длина + повороты.

## 5. Симуляция: как считать

> **Этап 2+ (после готовности редактора из §1 «Этап 1»).** Раздел — план на будущее,
> на этапе 1 не реализуется и не проектируется.

### 5.1 Формализм: MNA (Modified Nodal Analysis)
Стандарт для SPICE-подобных симуляторов:
- Узловые потенциалы + токи через вольтажники/индуктивности (доп. неизвестные).
- Матрица `G·x = b` (DC/AC) или с производными (transient).

**Система уравнений для элементов:**
- R: проводимость g = 1/R в узлах i,j.
- Источник напряжения: доп. неизвестная I_V; строка уравнений V_i − V_j = E;
  в столбец I_V записывается ±1.
- C (companion model, трапеция): G_eq = 2C/h, I_eq = −(2C/h)·v_prev − i_prev… (уточнить знаки в реализации).
- L: доп. неизвестная I_L; либо companion: G_eq = h/(2L), I_eq = i_prev + (h/2L)·v_prev.
- AC: всё комплексное (или расщепление на Re/Im), решение линейной комплексной системы.

### 5.2 Алгоритмы по типам анализа
| Анализ | Что решаем | Замечания |
|---|---|---|
| DC operating point | нелинейная система (если есть нелинейные эл.) через Newton–Raphson; для линейных — одна LU | «ноль итераций» для чисто линейной схемы |
| Transient | на каждом шаге h: companion-модели + LU (переиспользовать факторизацию, менять только правую часть при постоянной топологии); шаг h адаптивный (ошибка локально-экстраполяция) | для RC/LC/RL в MVP — аналитически корректно; BDF2/трапеция |
| AC sweep | комплексная LU на каждой частоте (лог. шаг по f), результат → |H(jω)|, φ | фазовые «графики-зонды» |
| Sweep параметров (опц.) | повтор DC/AC при изменении R/C/L/источника | крутой UX-бонус («график зависимости») |

### 5.3 Линейность: MVP-режим
Для старта — **только линейные элементы** (R, L, C, источники). Тогда:
- не нужен Newton–Raphson;
- transient можно решать через state-space (диагональные компаньон-модели) или общую MNA;
- матрица разреженная → sparse LU (или dense на старте: схемы «школьные», до ~100 узлов,
  dense-Холецкий на float64 — проще и надёжнее).

**Позже (не в MVP):** диод (exp-модель, лимитирование шага), транзистор BJT/MOS
(простые модели: Ebers–Moll / Shichman–Hodges), тогда — обязательный Newton–Raphson
+ source stepping + гашение.

### 5.4 Численная устойчивость (типичные грабли)
- Трапеция для LC даёт «неблокируемый» генератор шума (см. SPICE-фильтры; можно
  начать с Backward Euler — устойчиво, но «съедает» колебания).
- Идеальная L + идеальный источник → сингулярная матрица; вводить последовательное R (ESR) по умолчанию или «почти-ноль».
- Начальные условия: v_C(0), i_L(0) — редактируемые пользователем (IC).
- Длинные transient: кольцевой буфер сигналов (например, по 10k точек на канал),
  downsampling для отрисовки (min/max по бакетам).

### 5.5 Альтернатива: не писать solver самому
- Обернуть **ngspice** через cgo/CLI (вызвать `ngspice -b` сгенерированного netlist,
  распарсить raw-файл). Плюс: промышленная точность, AC/DC/transient/нелинейность «из коробки».
  Минус: cgo/бинарь-спутник, кроссплатформенная сборка сложнее, контроль шага — хуже.
- Go-библиотеки для numeric/sparse (напр., обёртки над LAPACK/CSPARSE) — если писать самому.
- **Рекомендация:** писать свой линейный MNA-солвер (обучательно и без cgo, полностью в Go),
  а ngspice держать как «режим эксперта» позже.

## 6. Отображение и UX

- **Камера:** pan (space/ПКМ/средняя кнопка), zoom (колесо, к курсору), масштаб 10%–800%.
  Трансформация едина для рендера и hit-test (обратная матрица).
- **Сетка:** 10 mil / 8 px шаг, snap при перемещении и рисовании; опция «привязка к пинам».
- **Визуал элементов:** векторные символы по IEC/ГОСТ (прямоугольник для резистора или зигзаг —
  на выбор; конденсатор — две пластины; катушка — дуги) — рисовать path'ами, не картинками
  (масштабируется чётко). Подписи: номинал + обозначение (R1 100 Ом).
- **Измерители:** амперметр — врезка в ветвь (как источник тока-«шунт»), вольтметр —
  параллельно узлам; «осциллограф» — зонд, привязанный к узлу → график внизу/в панели.
- **Панели:** слева — библиотека элементов (палитра), справа — инспектор параметров
  (значение, единицы, начальные условия, AC-параметры), снизу — временная диаграмма /
  таблица результатов, сверху — toolbar (undo/redo, запуск, тип анализа).
- **Запуск:** кнопка «▶» + выбор анализа (DC / Transient / AC) + настройки (длительность,
  шаг, частотный диапазон). Во время transient — живой график «прорастает» слева направо.
- **Схема «на лету»:** при перетаскивании — подсветка касающихся контактов, перерисовка
  rubber-band проводов; на mouse-up — пересборка netlist (см. §4.3).

## 8. Дорожная карта (этапы)

> Этапность закреплена решением из §1: **сначала редактор, потом физика.**

**Этап 0 — Spike (1–2 дня):** сравнить Gio vs Fyne vs Wails на одном экране:
«сетка + пара блоков + перетаскивание + коннектор + zoom». Замерить FPS и удобство.
Проверка: ядро принимает блоки без физической семантики (готовность к §1б).

**Этап 1 — Редактор (весь функционал §1 «Этап 1»):**
палитра → размещение → перемещение с snap → коннекторы между пинами →
живая перерисовка коннекторов → обработка пересечений/junction →
упорядочивание (align/distribute/слои) → undo/redo → save/load JSON.
*Физика НЕ подключается — блоки пока просто графика с подписями.*

**Этап 2 — Физическая привязка:** типы блоков становятся компонентами схемы
(R/L/C/источники/приборы), параметры с единицами, из геометрии коннекторов
собирается топология (union-find) → netlist. Валидации: «висящие концы»,
«нет общего провода», пересечения без junction подсвечиваются.

**Этап 3 — DC + Transient:** линейный MNA-солвер, RC/RL/LC, компаньон-модели,
графики напряжений/токов, зонды-«осциллографы».

**Этап 4 — AC-анализ:** комплексная матрица, Bode (амплитуда/фаза), синусоидальный
режим, векторные диаграммы (опц.).

**Этап 5 — Полировка:** авто-разводка проводов, коп/паст, библиотеки шаблонов схем
(делитель, резонансный контур, фильтр), экспорт SPICE/SVG, «примеры».
При желании — второй домен поверх ядра этапа 1 (mind map, flowchart).

**Этап 6 — Нелинейность (по желанию):** диод + Newton–Raphson + source stepping;
опционально интеграция ngspice.

## 9. Риски и подводные камни

1. **GUI-библиотеки Go** — главный риск: у каждой свои боли (DPI на Windows, рендер,
   нативность). Минимизировать рискованным spike'ом (Этап 0) и изоляцией `model/simulate`.
2. **Производительность перерисовки** при большом числе элементов → инвалидация только
   dirty-областей, spatial index, избегание аллокаций в hot-path (GC).
3. **Численная неустойчивость** transient (LC-осцилляторы) → начать с Backward Euler,
   документировать ограничения, позже трапеция+гашение.
4. **Сингулярные матрицы** (короткие замыкания, идеальные источники) → регуляризация
   (глубина заземления 1e-12 См), понятные ошибки пользователю («нет общего провода»).
5. **Определение топологии «на глаз»** (касания проводов без junction) — источник багов;
   нужен явный приоритет: пин > junction > проходящий мимо провод (и визуальная индикация).
6. **Delphi-привычки:** не увлекаться VCL-подходом; в Go лучше immutable-команды + явные интерфейсы.
7. **Кроссплатформенность:** тестировать Windows DPI/HiDPI сразу (Go GUI-библиотеки
   традиционно слабоваты в масштабировании).

### 13.1 Ретроспектива мозгового штурма (эволюция концепции)

| Шаг обсуждения | Что выяснили | Что закрепили |
|---|---|---|
| Старт | «Переписать школьный редактор схем (Паскаль/Delphi) на Go» | Среда: Go, desktop |
| Развилка 1 | Не обязательно электрика — может быть mind map → значит это **один и тот же generic node-edge editor** с доменами | Лежат вне ядра: электрика, деревья, flowchart |
| Развилка 2 | «Сначала редактор, потом физика» — двухэтапность | Этап 1 = чистый графический редактор; этап 2 = физика + мат. модели (§1, §8) |
| Итог | Этап 1 не только для схем: блоки/коннекторы/пересечения/порядок — уже самостоятельный продукт | Физику не скаффолдить на этапе 1 |

Что хорошо: постановка на два этапа сразу сняла главную развилку «продукт —
какой?» и дала этапу 1 самостоятельную ценность. Симулятор уже «припаркован»
подробно (§5) — детальное обдумывание не потеряется.

Что в шуме: документ содержит **много вперёд** про этап 2+ (симуляция, домены).
На этапе 1 работают только §1 «Этап 1», §2, §3, §4.1–4.4, §6 (UX камеры/сетка/
панели), §7, §8, §10. Остальное — черновик на будущее; в имплементации не открывать.

Открытых решений осталось 4 критичных (§10): платформа, GUI-фреймворк,
формат блоков этапа 1, необходимость автолейаута в этапе 1. Первые два блокируют
старт кода.

### 13.2 Как делаем (процесс)

- **Инкремент, а не горизонталь:** подзадачи UI и модели делаются вместе
  (вертикальный срез). Правило: *после любого дня работы билд запускается и что-то
  умеет*. Не «сначала весь model, потом весь render».
- **Каждый этап = запускаемый артефакт.** На этапе 0 это spike-бинарь; на этапе 1 —
  редактор, которым можно нарисовать и сохранить диаграмму; далее — по §8.
- **Отправные точки — одна истина без дублирования:** §8 — этапы, §10 — решения.
  Итог работы над спиком: 1 сессия = 1 заметка (что работает, что больно) → решаем.
- **Дизайн-отзыв:** после каждого этапа пользователь играет с билдом и даёт
  обратную связь «на ощупь» (удобство drag, сетка, отзывчивость) до перехода
  к следующему этапу — переработка UX на позднем этапе дороже.
- **Definition of Done** для каждой подзадачи этапа 1: код + ручной чек-лист
  (`спайк-чеклист.md`, см. §13.7) + юнит-тесты там, где есть вычислимая логика
  (hit-test, перестроение маршрута, undo/redo, save/load round-trip).

### 13.3 Раскладка работ внутри этапа 1 (под-инкременты)

Каскад: 1.0 → 1.1 → 1.2 → 1.3 → 1.4 → 1.5 → 1.6. Каждый — отдельный runnable.
*(Здесь детализация; сами этапы — §8.)*

- **1.0 Скелет:** окно приложения, канва (полноэкранная), камера (pan/zoom),
  сетка. Критерий: холст «живой» (гладкий zoom 10–800% к курсору, pan).
- **1.1 Блоки:** палитра слева, drag&drop на канву, перемещение, hover/
  выделение, удаление. Критерий: 50 блоков ворочаются плавно.
- **1.2 Коннекторы:** соединение пина с пином, snap к пинам, ортогональный
  маршрут (1–2 колена), **живая перестройка** при drag блока.
- **1.3 Пересечения и junction:** определение касаний, приоритет пин > junction >
  «мимо идёт»; пересечение без junction — без точки, только визуально; тесты
  hit-test на граничных кейсах.
- **1.4 Упорядочивание:** align/distribute — готов (A/R/T/B — края, H/V — центры,
  D/Shift+D — распределение; выделение: рамка на пустом, Shift+клик, Ctrl+A;
  drag группы со snap и push-apart).
- **1.5 Undo/redo, буфер обмена:** готово (undo/redo — снимки `core.History`,
  ленивое сведение холостых кликов; буфер — Ctrl+C/V, внутренние линки
  восстанавливаются, paste становится выделением; Del удаляет выделение).
- **1.6 Save/load JSON v1** — готов (`Document.MarshalJSON/UnmarshalJSON`,
  конверт `{schema,blocks,links}`, валидация+атомарность загрузки, Ctrl+S/O,
  путь=CLI-аргумент|schematic.json); автосейв и меню — НЕ НАЧАТО.
- Клавиатурные операции: 1..6 — блок с N пинами, Del — блок под курсором
  (+его линки), тянуть с пина — линк.
- (По желанию) **1.7 tidy-раскладка дерева** — только если решим, что автолейаут
  нужен (вопрос §10-8).

### 13.4 Архитектура этапа 1 (конкретизация §3, события входят)

```
sh_builder/
  cmd/shbuilder/main.go          # точка входа: boot GUI, wiring
  internal/
    geom/                        # Vec2, transforms, hit-test helpers (чистый Go)
    core/                        # модель документа (не знает про GUI)
      block.go                   # Block{ID,Kind,X,Y,W,H,Rot,Label}
      conn.go                    # Conn{ID,FromPt,ToPt,Geometry []Pt}
      document.go               # Document: коллекции, ops add/move/delete/rotate
      commands.go               # Command: AddBlock/Move/Delete/Connect/Align...
      history.go                 # undo/redo stack (commands в обе стороны)
      net.go                     # union-find: junction/crossing семантика (§4.3)
      save.go                    # JSON schema v1, версию поля data закрепить
    editor/                      # controllers: input state machine,
                                 # selection, drag, snap, clipboard
    render/                      # интерфейс Renderer (DrawBlock/DrawConn/...)
                                 # + сцена: слои, подсветка hover/selected
    ui/                          # палитра-инспектор-панели (реализация GUI)
```

- **Интерфейс `Domain`** (§1б) оставить «дыркой» на этапе 1 (палитра и рендер
  символов уже общаются через него) — этап 2 заполняет его без рефакторинга.
- **`render` через интерфейс:** чтобы spike не потянул за собой модель, если
  сменится GUI-фреймворк. Только `ui/` привязан к конкретному фреймворку.
- **wire-in-pattern:** input event → команда → document.ops → dirty-метки →
  перерисовка только затронутых (держим <16ms на 1000 элементов).
